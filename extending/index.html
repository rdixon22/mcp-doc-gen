    Extension Guide

    Cortex is designed to grow. All ingestion paths (HTTP, MCP, Discord) share the same library functions, and all MCP clients (Claude Desktop via stdio, Cursor via HTTP) are served by the same tool factory. Adding a new capability in one place exposes it everywhere.

    Adding a New MCP Tool

    All MCP tools are registered inside the createCortexServer() factory function in src/server/routes/mcp.ts. Both the HTTP /mcp endpoint and the stdio entry point (src/server/mcp-stdio.ts) call this same factory, so one registration covers all clients.

    Registration pattern

    // src/server/routes/mcp.ts  (inside createCortexServer())

server.registerTool(
  "my_new_tool",
  {
    title: "My New Tool",
    description: "What this tool does and when an agent should call it.",
    inputSchema: z.object({
      required_param: z.string().describe("What this param is"),
      optional_param: z.number().default(10).describe("How many results (default 10)"),
    }),
  },
  async ({ required_param, optional_param }) => {
    try {
      const result = await myLibraryFunction(required_param, optional_param);
      return {
        content: [{ type: "text", text: result }],
      };
    } catch (err) {
      return {
        content: [{ type: "text", text: `Error: ${String(err)}` }],
        isError: true,
      };
    }
  }
);

    Handler return contract

    Field Type Required Notes
    content Array<{ type: 'text', text: string }> Yes At least one element
    isError boolean No Set true when the handler catches an error instead of throwing

    Always catch errors inside the handler and return isError: true rather than throwing — uncaught exceptions crash the MCP request cycle.

    Input schema tips

    • Use zod objects for all input schemas. The SDK validates incoming calls against the schema before invoking the handler.
    • Add .describe("...") to every field — descriptions appear in the tool manifest that AI agents read.
    • Use .default(value) for optional parameters so handlers receive a usable value even when the client omits the field.

    Sharing Logic Between MCP Tools and REST Routes

    Business logic belongs in src/server/lib/, not in route files. Both MCP handlers and REST routes import from lib.

    Existing examples: - src/server/lib/capture.ts — captureThought() is called by POST /api/thoughts, the Discord bot (lib/discord.ts), and the capture_thought MCP tool. - src/server/lib/wiki.ts — readWikiPage(), writeWikiPage(), listWikiPages() are called by both routes/wiki.ts (REST) and multiple MCP tool handlers.

    Adding a new lib helper

    1. Create src/server/lib/my-feature.ts and export pure functions.
    2. Import from both the MCP tool handler in routes/mcp.ts and from a new or existing REST route.
    3. Add a test file at tests/server/my-feature.test.ts (see Testing conventions).

    Adding a new REST route

    1. Create src/server/routes/my-feature.ts exporting an Express Router.
    2. Mount it in src/server/app.ts: 
      import myFeatureRoutes from "./routes/my-feature.js";
app.use("/api", myFeatureRoutes);

    Adding a New Entry Source

    Every captured entry has a source string stored verbatim in entries.source. Current values: web, discord, mcp, api, wiki.

    To add a new source (e.g. slack):

    1. Capture: call captureThought(content, 'slack') from wherever you ingest the new data.

    2. Decide exclusion behavior: thought-only queries filter with source != 'wiki'. If your new source should also be excluded from thought-only results, update the exclusion filter in three places:

    3. src/server/routes/thoughts.ts — REST thought endpoints
    4. src/server/lib/discord.ts — Discord bot search

    5. src/server/routes/mcp.ts — the search_thoughts and list_thoughts tool handlers

    6. search_all is automatic: search_all uses source_filter: null (no filter) and will include the new source automatically with no changes needed.

    // Example: a new Slack ingestor
import { captureThought } from "../lib/capture.js";

async function handleSlackMessage(text: string) {
  const result = await captureThought(text, "slack");
  console.log(`Captured ${result.duplicate ? "(duplicate)" : "new"} thought: ${result.id}`);
}

    Adding a New Wiki Page Type

    Wiki page types determine which subfolder a page is written to and which values appear in page_type frontmatter. The canonical list lives in src/server/lib/wiki.ts.

    Step-by-step

    1. src/server/lib/wiki.ts — add to the WikiPageType union and WIKI_PAGE_TYPES array, and add a TYPE_DIR mapping entry: 

      export type WikiPageType =
  | "wiki_person"
  | "wiki_project"
  // ... existing types ...
  | "wiki_glossary";          // ← add here

export const WIKI_PAGE_TYPES: WikiPageType[] = [
  // ... existing entries ...
  "wiki_glossary",            // ← add here
];

const TYPE_DIR: Record<WikiPageType, string> = {
  // ... existing mappings ...
  wiki_glossary: "wiki/glossary",   // ← new subfolder
};

    2. src/server/routes/mcp.ts — update the zod enum in four tool definitions:

    Tool Parameter
    write_wiki_page type
    search_wiki type
    list_wiki_pages type
    migrate_vault_file target_type (only if the new type is a raw_* variant) 
    // Example: write_wiki_page type enum
type: z.enum([
  "wiki_person",
  "wiki_project",
  "wiki_concept",
  "wiki_area",
  "wiki_topic",
  "wiki_glossary",      // ← add here
  "raw_article",
  "raw_book",
  "raw_daily",
  "raw_attachment",
]).describe("Page type — determines which subfolder"),

    1. Database: if your Supabase schema enforces a page_type check constraint, update it in a new SQL migration file under supabase/migrations/.

    2. Filesystem: create the new subfolder under WIKI_VAULT_PATH before writing the first page of that type.

    Testing Conventions

    Tests live in tests/server/ and run with vitest. Ollama and Supabase clients are mocked — tests do not require running services.

    Reference file: tests/server/capture.test.ts — the canonical pattern for testing lib helpers.

    Adding a test for a new lib helper

    // tests/server/my-feature.test.ts
import { describe, it, expect, vi, beforeEach } from "vitest";

// Mock external dependencies before importing the module under test
vi.mock("../../src/server/lib/ollama", () => ({
  ollama: { embed: vi.fn() },
}));
vi.mock("../../src/server/lib/supabase", () => ({
  supabase: { rpc: vi.fn() },
}));

import { myLibraryFunction } from "../../src/server/lib/my-feature.js";
import { ollama } from "../../src/server/lib/ollama.js";
import { supabase } from "../../src/server/lib/supabase.js";

describe("myLibraryFunction", () => {
  beforeEach(() => vi.clearAllMocks());

  it("returns expected output for valid input", async () => {
    (ollama.embed as vi.Mock).mockResolvedValue({ embeddings: [[0.1, 0.2]] });
    (supabase.rpc as vi.Mock).mockResolvedValue({ data: [{ id: "abc" }], error: null });

    const result = await myLibraryFunction("test input");
    expect(result).toBeDefined();
  });

  it("handles Supabase errors gracefully", async () => {
    (supabase.rpc as vi.Mock).mockResolvedValue({ data: null, error: { message: "DB error" } });
    await expect(myLibraryFunction("test input")).rejects.toThrow("DB error");
  });
});

    Run the full suite:

    npm test

    Run a single file during development:

    npx vitest run tests/server/my-feature.test.ts
