    Cortex MCP Server Overview

    Cortex is a local-first AI second-brain: a system for capturing fleeting notes ("thoughts"), maintaining a structured knowledge wiki, and making everything semantically searchable — all from within an AI assistant conversation via MCP tools.

    The server is designed so that nothing leaves your machine. Embeddings are generated by a local Ollama instance, persistence lives in a local Supabase Postgres database with pgvector, and the wiki is a directory of plain markdown files on your filesystem.

    What Cortex Does

    Cortex manages two complementary knowledge stores:

    Thoughts are atomic, self-contained notes — observations, decisions, ideas, tasks, person notes, or references. When a thought is captured, Cortex automatically generates a vector embedding and calls a local LLM to extract structured metadata: the note type, topic tags, people mentioned, and any action items. Thoughts are stored in a Supabase entries table and are immediately searchable by semantic similarity.

    WikiVault is a curated, LLM-maintained knowledge base of structured pages — people, projects, concepts, areas, topics, and imported raw materials (articles, books, daily notes). Pages are markdown files with YAML frontmatter stored in a configurable directory (default ~/Documents/Obsidian/WikiVault/). Each page is also indexed into the same entries table so thoughts and wiki content can be searched together or independently. An index.md is rebuilt automatically, and every significant write is appended to log.md as an audit trail.

    Data Model

    All searchable content shares a single entries table in Supabase Postgres:

    Column Purpose
    content Raw text of the thought or wiki page body
    embedding 4096-dimensional vector from qwen3-embedding via Ollama
    source Origin: web, discord, mcp, api, or wiki
    metadata JSONB: type, topics, people, action_items
    file_path, title, page_type Wiki-only: filesystem location and page classification
    tags, wikilinks, page_sources, cortex_ids Wiki-only: relational context

    Deduplication is handled by a upsert_entry Postgres RPC that computes a SHA-256 fingerprint over normalized content. Semantic search uses a match_entries RPC with pgvector cosine similarity. Chat messages are stored in a separate messages table, also embedded and searchable.

    Functional Areas

    Thought Capture and Retrieval

    capture_thought is the primary ingestion tool. It takes a single string and handles embedding, metadata extraction, and deduplication automatically. Retrieval is served by three tools that cover different query patterns:

    • search_thoughts — semantic similarity search over thoughts only
    • list_thoughts — chronological browse with filters for type, topic, person, and recency
    • thought_stats — aggregate overview: total count, type breakdown, top topics and people

    Wiki Management

    The wiki tools follow a read-before-write discipline. read_wiki_page retrieves a page by title or file path (pure filesystem, no database). write_wiki_page creates or overwrites a page — it merges frontmatter, auto-extracts [[wikilinks]], re-embeds, and re-indexes. append_wiki_log appends an audit entry to log.md and should be called after every significant wiki action.

    Browsing is handled by: - search_wiki — semantic search restricted to wiki pages, with optional page-type filter - list_wiki_pages — filesystem scan returning title, type, tags, and path; no database required

    Cross-Corpus Search

    search_all queries the unified entries table without a source filter, returning both thoughts and wiki pages ranked by relevance. Results are labelled [thought] or [wiki:type]. It uses a lower default similarity threshold (0.45) for broader recall and is the right choice when you want the fullest possible context.

    search_messages searches the separate chat history (messages table), covering everything discussed in past AI conversation sessions.

    Vault Migration

    migrate_vault_file is a one-time import tool for bringing files from a MainVault (e.g. an existing Obsidian vault) into WikiVault's raw/ subtree. It strips Dataview blocks, adds standardized frontmatter, embeds, and indexes — without modifying the source file.

    MCP Transport

    Cortex supports two transports, both backed by the same createCortexServer() factory in src/server/routes/mcp.ts:

    Transport Entry point When to use
    stdio src/server/mcp-stdio.ts Claude Desktop — spawned as a subprocess
    Streamable HTTP POST /mcp on port 3001 Cursor, custom agents, any HTTP MCP client

    The HTTP endpoint accepts an optional x-cortex-key header or ?key= query parameter for authentication. If MCP_ACCESS_KEY is not set in the environment, authentication is skipped entirely.

    Companion Interfaces

    The same Node.js/Express process that hosts the MCP endpoint also serves:

    • REST API — /api/thoughts, /api/wiki, /api/chat, /api/conversations — used by the web UI and available for direct HTTP clients
    • React web UI — Vite + React 19 frontend on port 5173 with Capture, Browse, Search, and Stats tabs
    • Discord bot — optional; auto-captures messages in a configured channel and responds to !search, !recent, !ask, and !stats commands

    All three share the same core library functions in src/server/lib/ — particularly captureThought() in capture.ts and the wiki operations in wiki.ts — so behavior is consistent regardless of which interface is used.

    Multi-Step Usage Workflows

    Capturing and synthesizing knowledge

    1. Call capture_thought as insights arise throughout a session — each is embedded and tagged automatically.
    2. Later, call search_thoughts or search_all to retrieve relevant prior context on a topic.
    3. Call search_wiki or read_wiki_page to check whether a structured page already exists.
    4. Call read_wiki_page to read the existing page before modifying it.
    5. Call write_wiki_page to create or update the wiki page, synthesizing newly captured thoughts.
    6. Call append_wiki_log to record what was done.

    Answering a question with full context

    1. Call search_all with a broad query to get the widest possible picture.
    2. Follow up with search_messages to surface anything discussed in prior chat sessions.
    3. Use list_thoughts with a person or topic filter for targeted retrieval.
    4. Call read_wiki_page on any directly relevant wiki entries.

    Onboarding existing notes

    1. Call migrate_vault_file for each MainVault file, specifying the appropriate target_type.
    2. Call search_wiki to verify the imported content is indexed and searchable.
    3. Create or update wiki summary pages with write_wiki_page, linking to the raw imports via page_sources.

    Architecture at a Glance

    Claude Desktop          Cursor / custom agents
      │                         │
  stdio transport       HTTP POST /mcp
      │                         │
      └────────┬────────────────┘
               │
      createCortexServer()   ←── src/server/routes/mcp.ts
               │
       ┌───────┼───────────────────────┐
       │       │                       │
  capture.ts  wiki.ts            supabase.ts / ollama.ts
  (ingestion) (filesystem)       (persistence / inference)
       │                               │
  entries table              Ollama (qwen3-embedding,
  messages table              glm-4.7-flash, glm-5:cloud)
  (local Supabase            WikiVault markdown directory
   + pgvector)

    The MCP layer is a thin registration wrapper. All meaningful logic lives in src/server/lib/, making it straightforward to add new tools, REST routes, or ingestion sources that share the same capabilities.
