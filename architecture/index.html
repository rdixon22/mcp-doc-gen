    Architecture

    Cortex runs as a single Node.js (ESM) process that simultaneously serves REST routes, an MCP endpoint, and a Discord bot. A Vite + React 19 frontend on port 5173 proxies /api calls to the Express 5 backend on port 3001. A separate mcp-stdio.ts entry point is spawned as a subprocess by Claude Desktop when using the stdio MCP transport.

    Runtime Stack

    Layer Technology Default port / location
    Frontend Vite + React 19 http://localhost:5173
    Backend Node.js ESM, Express 5 http://localhost:3001
    MCP (HTTP) Streamable HTTP at /mcp http://localhost:3001/mcp
    MCP (stdio) src/server/mcp-stdio.ts subprocess stdio
    Bot discord.js (embedded in main process) —
    Inference Ollama OLLAMA_HOST (default http://localhost:11434)
    Database Supabase Postgres + pgvector (Docker) SUPABASE_URL

    Process entry points:

    • src/server/index.ts — starts Express on SERVER_PORT and calls initDiscordBot().
    • src/server/app.ts — constructs the Express app and wires all route modules; exported separately for testability.
    • src/server/mcp-stdio.ts — standalone entry point that calls createCortexServer() and connects via StdioServerTransport. Claude Desktop spawns this as a subprocess.

    Persistence Layer

    All captured content — thoughts and wiki pages — shares a single entries table in Supabase Postgres. The schema is defined in supabase/migrations/004_entries.sql.

    entries table key columns:

    Column Type Purpose
    id uuid Primary key
    content text Original content
    embedding vector(4096) Semantic embedding
    source text web, discord, mcp, api, or wiki
    metadata jsonb Type, topics, people, action items (thoughts)
    file_path text Relative path in WikiVault (wiki pages)
    title text Human-readable title (wiki pages)
    page_type text Wiki page type (wiki pages)
    tags text[] Topic tags (wiki pages)
    wikilinks text[] Extracted [[wikilink]] refs (wiki pages)
    fingerprint text SHA-256 of normalized content

    Deduplication is handled server-side by the upsert_entry RPC: if a row with the same SHA-256 fingerprint already exists, the RPC returns the existing row with duplicate: true rather than inserting a duplicate.

    Semantic search is handled by the match_entries RPC, which applies pgvector cosine similarity. The source_filter argument lets callers restrict results to thoughts only (['web','discord','mcp','api']), wiki only (['wiki']), or across all entries (null).

    Chat history lives in a separate messages table (joined to a conversations table), populated by the SSE chat endpoint in routes/chat.ts and searchable via a dedicated search_messages RPC.

    Inference Stack

    All inference runs locally through Ollama. Model names are configured in src/server/lib/config.ts and are overridable via environment variables.

    Role Default model Env var
    Embeddings qwen3-embedding (4096-d) EMBEDDING_MODEL
    Chat glm-4.7-flash CHAT_MODEL
    Metadata extraction glm-5:cloud METADATA_MODEL

    Embedding flow for a captured thought:

    1. captureThought() in src/server/lib/capture.ts calls Ollama to embed the content and extractMetadata() in parallel.
    2. extractMetadata() in src/server/lib/metadata.ts calls Ollama chat with a structured prompt; response parsing handles raw JSON, fenced code blocks, text-wrapped JSON, and <think> blocks, with a safe default on any failure.
    3. upsert_entry RPC writes (or skips) the row.

    The same captureThought() function is called by the HTTP REST route, the Discord bot, and the capture_thought MCP tool — there is no separate ingestion path.

    WikiVault Filesystem

    The WikiVault is a directory tree of markdown files at the path configured by WIKI_VAULT_PATH (default ~/Documents/Obsidian/WikiVault/). All file I/O is handled by src/server/lib/wiki.ts using gray-matter for YAML frontmatter.

    Directory structure:

    WikiVault/
├── wiki/
│   ├── people/
│   ├── projects/
│   ├── concepts/
│   ├── areas/
│   └── topics/
├── raw/
│   ├── articles/
│   ├── books/
│   ├── daily/
│   └── attachments/
├── SCHEMA.md
├── index.md   ← auto-rebuilt by write_wiki_page on new pages
└── log.md     ← append-only audit trail

    Every write_wiki_page call: 1. Merges with any existing frontmatter (preserves created, bumps updated). 2. Auto-extracts wikilinks[] from [[ref]] patterns in the body. 3. Writes the file via gray-matter. 4. Re-reads the file and calls upsert_entry with source='wiki' so the page participates in all semantic searches alongside thoughts. 5. Appends a log line to log.md and rebuilds index.md for new pages.

    Wiki pages are never stored only in the filesystem — the Supabase entries table always holds a synchronized, embedded copy.

    MCP Layer

    All 12 MCP tools are registered in a single factory function createCortexServer() in src/server/routes/mcp.ts. This factory is consumed in two places:

    • routes/mcp.ts mounts it behind the POST /mcp Streamable HTTP endpoint, with optional x-cortex-key / ?key= authentication controlled by the MCP_ACCESS_KEY env var.
    • mcp-stdio.ts calls the same factory and connects it via StdioServerTransport for Claude Desktop.

    Because both transports share one factory, adding a tool in createCortexServer() automatically exposes it to all MCP clients with no additional wiring.

    Tool handlers call into the same lib/ helpers used by REST routes and the Discord bot:

    MCP tool handler
  └─▶  lib/capture.ts  captureThought()
  └─▶  lib/wiki.ts     readWikiPage() / writeWikiPage()
  └─▶  lib/ollama.ts   ollama.embed() / ollama.chat()
  └─▶  lib/supabase.ts supabase.rpc('match_entries', …)
