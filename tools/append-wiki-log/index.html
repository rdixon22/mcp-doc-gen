    append_wiki_log

    Writes a single timestamped line to log.md in WikiVault documenting an action that was taken. This is the sole mechanism for maintaining an audit trail of all wiki mutations.

    Call this tool after every write_wiki_page call and after any other significant decision affecting the wiki. Skipping it breaks log continuity and makes the change history unreliable.

    Parameters

    Parameter Type Required Default Description
    file_path string ✅ Yes — Relative path of the page that was acted on (e.g. wiki/people/Alice-Smith.md)
    summary string ✅ Yes — One-line description of what was done. Maximum 200 characters.

    Parameter notes

    • file_path should be the relative path within WikiVault, matching the path returned by write_wiki_page or visible in list_wiki_pages results. Use the canonical path, not an alias or title string.
    • summary must be concise and self-contained. It should describe what changed and why in enough detail that someone reading log.md weeks later can understand the action without context. Hard limit: 200 characters.

    Returns

    Confirmation that the log entry was written to log.md, including the timestamp applied to the entry.

    When to call

    Trigger Required?
    After write_wiki_page (create or overwrite) ✅ Always
    After any significant decision about wiki structure ✅ Yes
    After migrate_vault_file ✅ Yes
    After a read-only operation (read_wiki_page, search_wiki, list_wiki_pages) ❌ No

    Usage examples

    Basic: logging a page update

    {
  "file_path": "wiki/people/Alice-Smith.md",
  "summary": "Added Q3 promotion note and updated role to Staff Engineer"
}

    Logging a new page creation

    {
  "file_path": "wiki/projects/Project-Phoenix.md",
  "summary": "Created new project page synthesising 4 captured thoughts from discovery phase"
}

    Logging a migration

    {
  "file_path": "raw/articles/notes-on-distributed-systems.md",
  "summary": "Migrated from MainVault; stripped Dataview blocks; indexed in Supabase"
}

    Typical write sequence

    Every wiki write operation should follow this three-step pattern:

    1. read_wiki_page — read current content to avoid clobbering
    2. write_wiki_page — write the updated content
    3. append_wiki_log — record what was done
    // Step 3 — called immediately after write_wiki_page succeeds
{
  "file_path": "wiki/concepts/Second-Brain.md",
  "summary": "Expanded definition section; linked to new wiki/projects/Cortex-Setup.md"
}

    Audit trail behaviour

    • All entries are appended to a single log.md file at the root of WikiVault.
    • Each entry is automatically timestamped by the server at the moment of the call.
    • Entries are append-only — append_wiki_log never modifies or deletes existing log lines.
    • The log is human-readable and can be reviewed directly in any markdown viewer.
