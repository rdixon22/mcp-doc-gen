    thought_stats

    Get an aggregate summary of everything captured in Cortex. Returns total thought count, a breakdown by type, the ten most frequently occurring topics, and the ten most frequently mentioned people — all computed in a single pass over the entries table with no embedding or LLM inference required.

    Use this tool to: - Quickly gauge how populated the knowledge base is - Surface dominant themes and recurring contacts - Verify that new captures are being classified correctly - Orient yourself before a deeper search or analysis session

    Parameters

    This tool takes no parameters.

    Parameter Type Required Default Description
    (none) — — — Stats are always computed across the full corpus of non-wiki entries.

    Returns

    A formatted text block containing:

    Field Description
    total Total number of captured thoughts (non-wiki entries)
    by_type Count for each thought type: observation, task, idea, reference, person_note
    top_topics Top 10 topic tags ranked by frequency of occurrence across all thoughts
    top_people Top 10 people mentioned, ranked by frequency

    Results are computed in-memory from the JSONB metadata column of the entries table. Only entries with source != 'wiki' are included — wiki pages are excluded from all stats.

    Usage example

    {
  "tool": "thought_stats",
  "arguments": {}
}

    Implementation notes

    • No inference required. thought_stats queries only the entries table — no Ollama embedding call or LLM metadata extraction is made. It is the fastest MCP tool to call.
    • In-memory aggregation. All non-wiki rows are fetched with an exact count, then iterated once in the server process to tally type distribution and topic/people frequency from the metadata JSONB column.
    • Scope is fixed. There is no way to filter by date range or source — the tool always reports on the entire corpus. To examine a slice of thoughts, use list_thoughts with its days, type, or topic filters instead.
    • Reflects current state. Because stats are computed fresh on each call against the live entries table, the numbers always reflect the current state of the database.
