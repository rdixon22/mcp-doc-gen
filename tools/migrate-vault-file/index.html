    migrate_vault_file

    One-time import tool that copies a markdown file from MainVault into the WikiVault raw/ hierarchy. During import it:

    • Parses and preserves the original frontmatter (stored as a comment at the bottom of the migrated file)
    • Strips ```dataview ... ``` blocks, replacing them with an HTML comment placeholder
    • Writes standardised frontmatter (type, status, source_path, imported date)
    • Embeds the body and indexes the page in Supabase via upsert_entry
    • Logs the action to the WikiVault audit log
    • Never modifies the original MainVault file

    Use this tool during a bulk one-time migration or to import individual articles on demand. To update an already-migrated file you must pass force: true; without it the tool refuses to overwrite.

    Parameters

    Parameter Type Required Default Description
    source_path string ✅ — Absolute path to the MainVault source file (e.g. /Users/alice/Documents/MainVault/Articles/some-article.md)
    target_type string (enum) ✅ — Page type that determines which raw/ destination subfolder receives the file. One of: raw_article, raw_book, raw_daily, raw_attachment
    force boolean ❌ false If true, overwrites the file if it already exists in WikiVault. If false (default) and the file exists, the tool returns an error without writing.

    target_type values

    Value Use for
    raw_article Articles, essays, web clippings
    raw_book Book notes and highlights
    raw_daily Daily notes and journals
    raw_attachment Other attachments or miscellaneous files

    The exact destination subfolder within raw/ is determined by the server's internal mapping for each type.

    Returns

    A text response confirming the import, including the destination path within WikiVault. On failure (e.g. file not found, target exists without force, filesystem error) the response describes the error condition.

    What happens during import

    1. The source file is read from source_path.
    2. Existing frontmatter is parsed via gray-matter.
    3. Dataview code blocks (```dataview ... ```) are stripped and replaced with <!-- dataview block removed -->.
    4. A standardised frontmatter block is written at the top of the new file, incorporating the target_type, a status value (mapped from any existing Status field), the original source_path, and an imported timestamp.
    5. The original frontmatter is appended as a YAML comment at the bottom of the file for reference.
    6. The file is written to the WikiVault raw/ subfolder corresponding to target_type.
    7. The page body is embedded via Ollama and indexed in Supabase (upsert_entry RPC, source='wiki').
    8. The action is logged to the WikiVault audit log.

    Usage examples

    Import a single article

    {
  "name": "migrate_vault_file",
  "arguments": {
    "source_path": "/Users/alice/Documents/MainVault/Articles/deep-work-summary.md",
    "target_type": "raw_article"
  }
}

    Import a book note

    {
  "name": "migrate_vault_file",
  "arguments": {
    "source_path": "/Users/alice/Documents/MainVault/Books/atomic-habits.md",
    "target_type": "raw_book"
  }
}

    Re-import (overwrite) an already-migrated file

    {
  "name": "migrate_vault_file",
  "arguments": {
    "source_path": "/Users/alice/Documents/MainVault/Daily/2024-01-15.md",
    "target_type": "raw_daily",
    "force": true
  }
}

    Important notes

    • source_path must be an absolute path. Relative paths are not supported.
    • The original MainVault file is never touched. Only the WikiVault destination is written.
    • force: false (default) is safe. Without force, the tool will not overwrite an existing WikiVault file, making repeated calls to the same source idempotent.
    • Dataview blocks are destructive-stripped. Their query logic is lost; only the placeholder comment remains. Review migrated files if Dataview output was important.
    • Call append_wiki_log manually if you need additional audit entries beyond the automatic one written during import.
    • This tool targets raw/ page types only. To create structured wiki pages (people, projects, concepts, etc.) use write_wiki_page instead.
